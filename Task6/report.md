## Метрики для эффективности классификации:

| Метрика                 | Что показывает                                              | Как помогает оптимизировать систему                               |
|-------------------------|-------------------------------------------------------------|-------------------------------------------------------------------|
| Classification coverage | Доля полей/файлов, которым присвоен класс данных            | Показывает, сколько данных остаётся «неразмеченными»              |
| Precision               | Насколько точно движок помечает данные как конфиденциальные | Снижает ложные срабатывания и лишнюю блокировку данных            |
| Recall                  | Насколько полно движок находит конфиденциальные данные      | Снижает риск попадания ПДн/медтайны в открытые аналитические слои |
| False positive rate     | Доля обычных данных, ошибочно признанных чувствительными    | Помогает не усложнять работу аналитиков                           |
| False negative rate     | Доля чувствительных данных, не найденных классификатором    | Главная security-метрика, её нужно минимизировать                 |
| Confidence score        | Уверенность классификатора по каждому полю/файлу            | Данные с низкой уверенностью отправляются в Quarantine            |
| Schema drift count      | Количество новых или изменённых полей во входных данных     | Помогает быстро замечать изменения в источниках                   |
| Quarantine rate         | Доля данных, отправленных в карантин                        | Показывает качество правил и стабильность входных схем            |
| Processing latency      | Время от загрузки данных до классификации                   | Помогает оценивать SLA batch-загрузки                             |
| Throughput              | Количество обработанных записей/файлов в минуту             | Показывает, выдерживает ли система рост данных                    |
| Manual review rate      | Доля данных, требующих ручной проверки                      | Помогает понять, где нужны новые правила классификации            |
| Reclassification rate   | Доля данных, у которых изменился класс после проверки       | Показывает качество первичной классификации                       |

## Масштабирование:

Масштабируемость обеспечивается за счёт разделения процесса на независимые компоненты. Каждый компонент можно
масштабировать отдельно.

| Компонент               | Как масштабировать                                 |
|-------------------------|----------------------------------------------------|
| Batch Ingestion Service | Горизонтально, несколько worker-подов              |
| Landing Zone            | Object Storage: S3, масштабирование по объёму      |
| Schema Profiler         | Параллельная обработка файлов/таблиц               |
| Classification Engine   | Горизонтальное масштабирование stateless-инстансов |
| Masking & Anonymization | Очередь задач + worker-поды                        |
| Quarantine              | Отдельный bucket/table partition                   |
| Data Catalog            | Отдельная БД метаданных, индексы                   |
| Analytical Storage      | Партиционирование, шардинг, реплики                |
| Metrics                 | Prometheus + Grafana, retention policies           |

## Расширение системы при росте нагрузки:

1. При росте объёма batch-загрузок добавить:
    * больше ingestion-workers
    * партиционирование по источнику и дате
    * очередь задач
    * параллельную обработку файлов
2. При росте количества источников добавлять адаптеры источников. Сам Classification Engine при этом не меняется.
3. При росте количества пользователей BI/ML разделить слои доступа:
    * Bronze Restricted — только data engineers/security
    * Silver Protected — аналитики с расширенными правами
    * Gold Analytics — BI/ML-пользователи
4. При росте нагрузки на классификацию использовать очереди задач: Landing Zone → Queue → Classification Workers →
   Protected DWH Layers. При таких условиях система будет масштабироваться количеством воркеров.

## Резюме:

Эффективность классификации оценивается через coverage, precision, recall, false positive rate, false negative rate,
quarantine rate, schema drift count, processing latency и throughput. Основной приоритет — минимизация false negative
rate, так как пропуск чувствительных данных создаёт риск попадания ПДн и медицинской тайны в аналитические слои без
защиты.

Масштабируемость обеспечивается за счёт stateless-компонентов, горизонтального масштабирования
ingestion/classification/masking workers, использования object storage для landing zone, партиционирования данных по
источнику и дате, а также разделения аналитического хранилища на Bronze Restricted, Silver Protected и Gold Analytics.
При росте объёма данных добавляются worker-поды и очереди задач, при росте числа источников — новые source adapters, при
росте числа пользователей — отдельные витрины Gold Analytics и разграничение доступа через Policy Engine.
